1. One token, one layer

The router picks 8 of 128 experts. Each one is three int4 matrices of 2048×768, 2.65 MB together. Per token per layer that is 21 MB read from memory against well under 0.1 MB of activations, so decode is a pure memory problem. Stock mlx-lm spends 6 GPU dispatches on the expert part; our kernel spends 3.

2. How close are we to the hardware?

The datasheet says 273 GB/s; a read-only kernel measured 240–250 GB/s (copy: 224). Per-call time comes from the slope of total time vs chain length (10 to 80 calls), which removes the 130–340 µs fixed cost of every eval. With 80 non-repeating routings (no cache reuse between calls), our T=1 kernel reads at 94% of the floor on Qwen3 and at the hardware limit on gpt-oss and Mixtral. Stock mlx-lm reaches 77% on Qwen3.

3. Where the T=1 gain comes from

Qwen3 +16.8%, gpt-oss +11.7%, Mixtral +2.9%.

MLX's fast qmv needs K % 512 = 0. Qwen3's down projection has K=768 and gpt-oss has 2880, so both drop to the slow path.

Change only that dimension (768→1024) and our gain falls 1.17 → 1.10.

4. Real routing breaks the uniform assumption

We recorded the router of Qwen3-30B-A3B on about 5.4k tokens of English technical prose, Python and Polish (48 layers). Consecutive tokens reuse experts heavily. At T=8 (a speculative-decoding verify step) there are 64 slots but only about 28 distinct experts, yet both stock MLX and our first kernel read the weights once per slot.

At T=8: slots 64, uniform 51.6, batched 42.6, consecutive 28.

5. Exploiting reuse: autoresearch, round 1

A Karpathy-style autoresearch loop ran overnight. The agent may edit one file and is scored by a read-only evaluator (correctness gate plus interleaved A/B against real mlx-lm on real routing traces). Every kept or discarded experiment is a git commit. The winner groups the slots of one step by expert in a map prepass, then runs simdgroup_matrix 8×8 with an exact q | 0x6400 int4→half dequant, so each expert's weights are read once per tile of up to 8 tokens.

MMA: 1.16, 1.22, 1.36, 1.64, 1.87, 2.36 at T=1..32.

Re-verified with seeds the agent never saw, 8 routing windows per launch, CIs resampled by launch: T=8 1.75 [1.63, 1.83], T=16 2.02 [1.90, 2.13].

An earlier ±1–3% CI was too narrow (audit 2).

5b. Same idea, the gpt-oss format: MXFP4

MXFP4 stores each weight as a 4-bit float (E2M1) with one power-of-two scale per 32 weights: 4.25 bits, no bias term. Round 4 of autoresearch ported both kernels to it. The key trick decodes two FP4 values into a half2 with a single bit expression, exact including subnormals, and folds the leftover 214 into the scale. Every point below beats mlx-lm's own MXFP4 path, including shapes outside the MXFP4 tuning bench.

Correction: the first version overflowed a half scale on real checkpoints (E8M0 ≥ 129, ~11% of gpt-oss down groups). It was found by running the real gpt-oss and fixed with a regression test. The first fix cost 8–11% at T ≥ 16. Round 5 then applied the scale in fp32 per 32-group (exact for every scale byte; it also caught a second overflow at bytes ≥ 241) and won most of that back. The chart shows round-5 numbers.

Qwen3 traces: 1.26 to 2.42; gpt-oss-20b: 1.16 to 1.69.

Decoding FP4 costs about the same as int4: no bias term and no x prescale pay for the bit trick.

So MXFP4 is faster than int4 by roughly its byte ratio: Qwen3 T=1 at 106 vs 114 µs.

6. Does it hold end to end?

Production dispatcher metal_q4_moe: the v4 GEMV at T=1, the MMA tile kernel at T>1. The verify benchmark feeds the same fixed text through the full model in chunks, the way a speculative-decoding verify step does, so both arms do identical work.

Chunk 1: 74.5 vs 79.9; 2: 102.6 vs 110.2; 4: 124.4 vs 148.6; 7: 128.4 vs 167.6; 16: 193.8 vs 271.8 tok/s.

The whole model, attention included: +23% at 4 tokens, +34% at 7, +45% at 16.

Pitfall: once the two arms generate different text, draft acceptance differs (0.63 vs 0.54) and tok/s no longer compares kernels. That is why the verify benchmark exists.

Quality: teacher-forced perplexity on a frozen 1000-token corpus is 21.17 (stock), 21.15 (ours) and 21.02 (fp32 experts). All pairs agree on top-1 95.8–96.2% of the time, which is the model's bf16 noise floor. Layer-level error vs fp32 is 2× lower for our kernel (3.5e-3 vs 6.9e-3).

Surprise: on this MoE, speculative decoding with a 0.6B draft is slower than plain decoding for stock MLX (72–77 vs 91.5 tok/s). With our kernel it is roughly break-even.

8. Questions worth your eyes

  • Solved: why did our untiled kernel gain on Mixtral as T grew? With 8 slots on 8 distinct experts, both kernels run at ~260 GB/s. With 8 slots on 2 experts, MLX still takes 3063 µs but ours takes 2243 µs. Our grid runs slots of the same expert concurrently, so their weights come from cache. MLX orders the batch outermost and re-reads. What else does dispatch order decide?
  • Layer 0 routes nearly at random while deeper layers reuse ~50%. Should the kernel choose its strategy per layer?
  • Speculative decoding loses to plain decoding on this MoE. Would an expert-budgeted draft (MoE-Spec style) or MTP heads flip that, now that verify cost is ~1.6× cheaper?
  • The MMA kernel needs d % 128 = 0, so gpt-oss (2880) uses the scalar tile kernel. Is a tail path worth it?
  • Same study on NVIDIA (Triton, Marlin-MoE) is still to run. The harness is ready; it needs a Modal login.

How this was done

Karpathy's protocol, adapted: know the data first (real routing traces), dumb baselines plus a roofline, correct before fast, one change at a time with numbered kernel versions (v1 → v31 → tiles), the human writes program.md and the agent edits one file, keep/discard by a fixed metric with git, and an adversarial audit before any claim.
